# RTC stale table snapshot can restore a deleted top-level paragraph

## Summary

Fuzz signature `da361be57ba6` exposes a real RTC block-merge bug in the post editor. A collaborator can insert a top-level table after a paragraph, another collaborator can delete that paragraph, and a later stale full-block snapshot from the table author can restore the deleted paragraph above the table.

The original realistic WebSocket repro uses normal editor actions:

1. Start with three top-level paragraphs.
2. User A deletes the middle paragraph.
3. User B inserts a top-level `core/table` after `Shared editing target paragraph.`.
4. User A deletes `Shared editing target paragraph.`.
5. User B sends a stale full block snapshot that still contains the deleted paragraph and the table.

Expected final blocks:

```text
Seed 951444 baseline paragraph.
core/table
```

Observed failure on vulnerable merges:

```text
Seed 951444 baseline paragraph.
Shared editing target paragraph.
core/table
```

## Root Cause

`mergeCrdtBlocks()` merges a full block array from the local editor into a shared `Y.Array`. The vulnerable path treats the incoming full array as authoritative and diffs it positionally against the current CRDT array. When the incoming snapshot is stale, a block that was deleted remotely but still exists in the local editor snapshot is interpreted as a local insertion.

This is especially visible with a table at the tail because the right-side diff can keep the table matched while inserting the stale deleted paragraph immediately before it.

The required May 7 known-fixes base `f256024286dd80a4c0e2579f658c109256abf648` added stale local snapshot reconciliation for the no-explicit-base path, but pass 180 found a remaining explicit-base gap: if `mergeCrdtBlocks()` receives `baseBlocks`, exact `f256` bypasses stale reconciliation and still restores `Shared editing target paragraph.`. A later local branch commit, `c8af86c24a5c70784e4604b66b772a0511859a00`, fixes that specific explicit-base gap by reconciling with `baseBlocks` too.

## Practical Impact

This needs two live collaborators editing the same post through the RTC sync path. The block operations are ordinary: paragraph deletion and table insertion. The timing is the uncommon part: one peer must send a stale full block snapshot after receiving a remote delete.

Impact is content corruption/loss of intent. A deleted paragraph can reappear in another editor session and can become persistent post content if that session saves. There is no evidence for a save loop, database corruption outside post content, OOM, or broad single-user exposure.

The user-facing likelihood is low on unfixed RTC builds because the actions are normal but the stale interleaving is narrow. On a base that includes stale snapshot reconciliation for both no-base and explicit-base paths, the likelihood should be very low for this signature.

## Fix Direction

Reconcile stale local full-block snapshots against the last local base, or an explicit `baseBlocks` argument when present, before running the positional merge. A block ID that was present in the base and still present in the stale local snapshot but is absent from the current CRDT array should be treated as remotely deleted and filtered out. A current remote block ID absent from the stale local snapshot and the base should be preserved and inserted into the local snapshot before the positional merge.

This keeps ordinary local edits while preserving remote top-level inserts and deletes.
