# CI Test Flake Analysis - 2026-05-01

This is a point-in-time analysis of Gutenberg CI flakes as of 2026-05-01, generated on branch `try/test-flakes`. The primary signal is the repository's own Playwright flake reporter, which opens or updates GitHub issues labeled `[Type] Flaky Test` when an E2E test passes after retry. The E2E workflow runs Playwright in 8 shards and archives `test/e2e/flaky-tests` reports before `packages/report-flaky-tests` writes GitHub issues.

Scope note: GitHub search reported 676 total historical issues with `[Type] Flaky Test`; this file analyzes the 112 currently open issue records, consolidated to 106 unique `(test title, test path)` flakes. Closed historical issues are useful for archaeology, but including every closed duplicate would mostly measure old cleanup policy rather than current CI risk. Unit/PHP nondeterminism is not covered here because the current in-repo reporter only classifies Playwright E2E retries as flakes.

## Data Sources And Method

- GitHub Search API query: `repo:WordPress/gutenberg is:issue is:open label:"[Type] Flaky Test"`, fetched 2026-05-01.
- In-repo reporter code: `test/e2e/config/flaky-tests-reporter.ts`, `.github/workflows/end2end-test.yml`, and `packages/report-flaky-tests/src/*.ts`.
- Source-history introduction: for each unique test, `git log --reverse -S <test title> -- <test path>` against local `origin/trunk` at `e1e460ae2c8`; if the exact title search failed, the first file-touching commit was used. This identifies when the current test case or its Playwright form entered the suite, not a proven product-code regression point.
- Latest failure class: parsed from the most recent retained stack in the flake issue body. Older issue entries are often summarized without stacks, so this is a classification aid, not a complete failure taxonomy.

- Stale but still open: 12 unique flakes have no retained reporter sighting in 2026. They should not be treated as current failures without a new run reproducing them.

The collection has two different problems mixed together: real product/test races, and infrastructure flakes. By latest retained failure class, 57 of 106 unique open flakes currently end in `socket hang up` from Playwright API requests to the local WordPress server. That does not prove every one of those tests is healthy; it does mean the current issue list is polluted by environment failures and cannot be used directly as a product-bug priority queue.

The highest-impact real test races are more concrete: homepage page-row fixture collisions, DataViews focus-order assertions, post-content-focus-mode canvas selection timing, classic/media-modal actionability, save-lock upload races, and navigation/interactivity hydration races.

## Targeted Cluster Deep Dives

These are the clusters inspected beyond issue metadata and source-history search. They are the most actionable first fixes.

### Homepage Settings

The top flake is fixture leakage. `homepage-settings.spec.js` seeds `Sample page` in `beforeAll` without first deleting existing pages, then selects by `getByLabel( 'Sample page' )`; CI has resolved both `Sample Page` and `Sample page`. This was introduced by #67650 / `9bdbadaa011`, which added the posts-page action coverage. Fix fixture isolation first: delete all pages before seeding or use generated unique titles/page IDs; selector-only fixes are weaker because they leave shared state ambiguous.

### Post Content Focus Mode

The failing test inserts `Initial content`, toggles Show template, waits only for a header block, and then calls `editor.selectBlocks()` on text inside the canvas. `selectBlocks` times out while looking for a `data-block` attribute, so the race is template/canvas readiness. It was introduced by #76305 / `9eec17489a4`. Fix by isolating template fixtures, waiting for the Post Content block and inner paragraph to be visible and attached after Show template is enabled, then selecting by block document/client id rather than text alone.

### Publish Panel

The focus-return test clicks Cancel and immediately expects focus on the top-bar Publish toggle. The latest failure still had `aria-expanded="true"`, meaning the panel had not closed. The focus behavior was introduced with #45623 / `8b6e1c50b5d`, which used timeout-based focus handling to avoid `useFocusReturn` capturing the wrong element. Fix the test to wait for panel closure or `aria-expanded=false` before asserting focus; if this still flakes, move most of the behavior to lower-level focus tests and keep one E2E smoke path.

### Upload Save Lock

The upload-lock tests intentionally hold media REST requests, poll `isPostSavingLocked()`, then separately check the Save draft button. The implementation drives the button from the lock selector, but lock lifetime differs across client-side processing and server upload handoff. This was introduced by #76973 / `211c39cfec7`. Fix the product/test boundary so the lock covers the whole upload lifecycle deterministically; in the test, count expected uploads and poll lock plus button disabled state atomically.

### User Global Styles Revisions

`saveRevision()` dispatches `editEntityRecord()` and immediately calls `saveSiteEditorEntities()`. The helper chooses Save or Publish based on a one-time `isVisible()` check, and the latest failure chose Publish before a Publish button existed. The pagination test was introduced by #56799 / `0167c532094`. Seed revisions through REST/request utils for the pagination test, or wait for dirty global-style state and a concrete visible top-bar Save/Publish button before clicking.

### DataViews Keyboard

DataViews focus flakes all come from fixed key sequences over an async list. The tests press Tab/arrow keys after only grid visibility; the list can be visible but `inert`, and composite active item state does not guarantee DOM focus. Original keyboard coverage came from #61648 / `23efd8d8`; newer action-button flakes line up with later visible-but-inert refreshing and focus guard changes. Fix by waiting for a stable keyboard surface: search focused, toolbar buttons visible/enabled, grid visible and not inert, and first composite item active/tappable before key presses.

### Interactivity Router

Router-region issue #77704 waits on old content after navigation, so the second click can target the wrong page. Align the start page with the test comment and wait on changed URL/title/content after every navigation. Router-navigate issue #77197 has explicit resolver races: pending count can increment before the route fetch resolver exists; the timeout test can also block document navigation. Await named fetch-capture promises and block only fetch/XHR requests where intended. Router-script-modules #71195 is currently an afterAll `socket hang up` during theme/plugin cleanup, not a script-module assertion failure.

### RTC Collaboration

Collaboration notes wait for generic sync responses, but the `All notes` button renders only after receiver-side note/comment records exist. Poll receiver state or visible note metadata before opening the sidebar. The block gauntlet inserts setup blocks through slash commands and only waits for a count, so a transient `/pul` paragraph can satisfy the count but break strict locators; create the initial block set deterministically or wait for exact names/content and absence of slash placeholders. The stress tests need phase-level sync barriers, local per-user assertions, and save waiting that does not assume a single unique `Draft saved` snackbar.

### Navigation And Inserter

Many Navigation and Inserter entries are currently mislabeled by the test title because the retained failure happens during REST setup or cleanup, not the UI assertion. Examples include `deleteAllPages()`, `deleteAllBlocks()`, and `deleteAllWidgets()` surfacing `socket hang up` through `requestUtils.rest()`. Treat those as a `RequestUtils`/wp-env transport problem first. The real Navigation assertions still have specific races: `publishPost()` can click Save/Publish and then choose the wrong next button if the entity-save panel appears late, and the `openSubmenusOnClick` migration test manually saves then immediately reads REST content before persistence is guaranteed. Fix the transport layer with retry/backoff and diagnostics, then fix the save helpers so they wait for either entity Save or Publish state deliberately.

### Classic, Image, And External Media

The Classic block flake is a real UI state issue: after undo, the test checks that the Classic block is visible, but not that it is selected, and then tries to click `Convert to blocks` through the toolbar. Explicitly select/focus the Classic block after undo before using the toolbar, or expose a block-command helper that is independent of hover toolbar visibility. Image drag/link tests also depend on external resources such as Openverse and remote image URLs; in CI those should be mocked or replaced with local media fixtures.

### Template Revert

The oldest Template Revert flakes mixed semantic equality with raw string equality: reordered JSON keys, default query attributes, or whitespace could fail even when the block tree was equivalent. A targeted fix already moved part of this area toward `getEditedPostContent()` and fixture alignment, so old release-branch reports should be closed or backported deliberately. The current open Template Revert sightings are more often `socket hang up` during `deleteAllTemplates()` setup/cleanup, which belongs with the `RequestUtils` transport fix.

## Collection Analysis

### 1. The issue list is not a clean flake backlog

The reporter intentionally records tests that pass after retry, but the open issue list includes stale historical rows, duplicate issue rows, and infrastructure failures. The 6 duplicate open issue pairs show that issue lifecycle is not reliable enough for prioritization. The reporter matches by issue title, fetches `state: all`, and may reopen old closed issues or create new ones depending on ordering and merge-base logic. It should key on `(normalized title, normalized path)`, prefer an existing open issue, and close/mark duplicates.

### 2. The dominant current failure class is infrastructure-shaped

A latest retained `socket hang up` appears in 57 unique open flakes and 3,764 retry events. Those failures often happen in request setup/cleanup, not at the named assertion. Treating them as independent product flakes wastes effort and hides a systemic wp-env/server-health issue. The fix plan should first classify these as infrastructure, capture server/container logs, and mark them separately from deterministic test assertion races.

### 3. Real UI flakes cluster around async focus, hydration, and entity persistence

DataViews keyboard tests assume a fixed focus sequence after `grid` visibility. Site editor and navigation tests assert frontend/editor state after saves, route transitions, style propagation, or Interactivity API hydration. Upload and media tests intentionally hold REST requests and then expect store and toolbar state to move together. These are legitimate E2E surfaces, but the tests often wait for a visual proxy instead of the state transition being asserted.

### 4. Several high-volume flakes are old Playwright migrations

Many open flakes entered during Playwright migrations in 2022-2024. That does not mean Playwright caused the product behavior; it often means a broad, user-like test was preserved without adding deterministic readiness signals. Long-lived flaky tests need ownership: fix, rewrite, quarantine with owner/date, or delete if the behavior is now covered elsewhere.

## How Flakes Were Introduced

The per-row `Introduced by` column captures individual introductions. At the collection level, introductions fall into these patterns:

- New feature coverage landed before the feature had a stable test readiness signal, e.g. RTC collaboration, upload save-lock, router region preservation, DataViews keyboard navigation, and post-content focus mode.
- Legacy E2E flows were migrated to Playwright, preserving broad UI workflows while changing timing/actionability semantics, e.g. inserting-blocks, Classic, template revert, comments, widgets, and undo tests.
- Tests created shared or ambiguous fixtures, e.g. homepage-settings uses broad page-row locators and can match duplicate page titles.
- Tests assert frontend state after editor/global-style/entity persistence without waiting for the persistence boundary that matters.
- CI infrastructure failures are being reported under the affected test name, so the issue appears to have been introduced by the test while the actual cause may be wp-env, REST server health, Docker, or shard-level resource pressure.

## Initial Fix Plan

1. Fix reporter hygiene first: dedupe open flake issues by `(title, path)`, prefer open issues over closed ones, stop reopening stale duplicates when a current open issue exists, and add labels for `infra`, `focus`, `hydration`, `fixture`, and `state-race`.
2. Separate infrastructure from test assertion flakes: classify `socket hang up`, browser/context-closed, and setup hook timeouts separately; upload wp-env/Docker logs and request timing for every shard; add a server health check before requestUtils calls.
3. Fix the top active real flakes by volume: homepage fixture collision, post-content-focus-mode canvas selection race, DataViews focus assertions, upload-save-lock synchronization, classic media modal actionability, and global-styles pagination actionability.
4. Create subsystem sweeps for Navigation, Interactivity router, Site Editor template persistence, Inserter, Media, and RTC. Each sweep should reduce broad UI workflows into smaller tests with explicit state readiness signals.
5. Quarantine only with owner, expiry, issue link, and reproduction command. Do not add blind retries as a fix.
6. Validate fixes with `npm run test:e2e -- <spec> --repeat-each=N` locally or in CI, then monitor at least 50 trunk E2E runs before closing high-volume flake issues.

## Review Of The Initial Plan

### Linus Torvalds lens

The plan must not hide broken tests behind labels and process. The useful part is attacking concrete top offenders and deleting duplicate/stale bookkeeping. The weak part is any wording that allows "infra" to become an excuse. If the local server falls over, that is also a bug in the CI system, and it needs logs, a reproducer, and an owner. No new abstraction should be added until a repeated failure demonstrates the need.

### Kyle Kingsbury / Jepsen lens

The plan needs better histories. A flaky E2E run is a distributed trace across browser, WordPress REST, database, iframe editor, frontend route, and sometimes multiple clients. The current report stores a final stack, not enough causal context. For RTC and router flakes, add explicit event histories, clocks/sequence IDs, and quiescence predicates. Tests should state what invariant is expected after which operations have completed; otherwise a retrying assertion is just sampling an eventually consistent system at arbitrary times.

### Dan Luu lens

The biggest risk is spending days hero-debugging memorable UI flakes while the actual CI pain is dominated by boring infrastructure and stale issue hygiene. Measure base rates, close stale rows, rank by expected saved CI minutes, and make failures cheaper to triage. The plan should include mundane ownership and dashboards because flaky-test work fails when it depends on occasional heroic attention.

## Revised Fix Plan

1. Build a clean flake ledger. Generate a daily machine-readable table keyed by `(title, path)` with open issue numbers, first/last seen, retry count, trunk count, latest failure class, and owning package/spec. Close or mark stale any open issue with no sighting in 90 days, and automatically cross-link duplicates.
2. Split reporting into `test assertion flake` and `environment flake`. Do not file or update the test issue for `socket hang up` without attaching wp-env logs, server health, shard id, and failing API route. File those under a separate infrastructure issue if they recur across unrelated specs.
3. Fix the current high-signal flakes in this order: homepage-settings duplicate fixture names; post-content-focus-mode canvas readiness; DataViews keyboard focus readiness; upload-save-lock upload-count synchronization; Classic post-undo block selection; Openverse/external-media isolation; global-styles pagination readiness.
4. For each subsystem, add one reusable readiness helper only after two or more tests need the same predicate: DataViews grid focus-ready, router idle/request captured, editor entity saved, frontend style applied, media upload complete, RTC all-clients-synced.
5. Quarantine only tests that are both high-cost and not fixable in one sitting. Every quarantine entry must include owner, expiry date, reproduction command, current failure class, and issue link. Expired quarantines fail CI.
6. Use repeat validation, not optimism. A candidate fix is not done until the target spec passes repeated runs and the trunk flake ledger shows zero new sightings for a fixed observation window.
7. After the first pass, reconsider old open flakes with low or stale activity. Either reproduce and fix them, close as stale with a bot rule that reopens on a new sighting, or delete tests whose behavior is covered by lower-level tests.
