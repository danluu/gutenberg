# Audit: Gutenberg PR 77889 vs PR 77890

Date: 2026-05-02

Compared changes:

- PR 77889: `2a3963211eea81d66a0c88c2bf2ceab660d1b5e7`, "RTC: Add base version tracking to prevent stale CRDT doc overwrites"
- PR 77890: `bd511b424f1e7077a59fb7f61f2f24cbd3b3c7eb`, "RTC: Reject stale persisted CRDT documents"

This is a static audit of the two implementations. I did not run the full test suite. I used the named reviewers in the request as audit lenses: low-level invariants, concurrency histories, operational failure modes, security boundaries, and small/simple trusted code.

## Executive Judgment

Neither PR should merge as-is.

PR 77890 is the better starting point. It has the right user-visible shape: content-derived base versions, explicit REST `409` conflicts, a client refetch/merge/retry path, public sync-manager support for applying a freshly fetched persisted CRDT document, and targeted tests.

PR 77889 has the most important missing primitive: a database-level compare-and-swap on the meta row. However, its client retry path is effectively wrong, its successful-save detection misclassifies normal saves as conflicts, its initial-version hook does not exist in WordPress metadata, and it has no test coverage.

The right fix is not to pick either PR wholesale. Use 77890's client protocol and tests as the base, add an actual atomic write path from 77889, and carry over 77889's autosave stripping.

## High-Severity Findings

### 1. PR 77890 does not have an atomic freshness check

PR 77890 validates freshness before the metadata write:

- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:192` reads the current `_crdt_document`.
- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:204` computes the current document version.
- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:214` accepts a matching incoming `baseVersion`.
- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:241` wires that validation into `update_post_metadata`.
- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:299` adds an earlier REST pre-insert check.

Those checks are useful for error reporting, but they are not a linearization point. Two requests can both read the same current value, both pass validation, and then WordPress metadata update can serialize them as last-writer-wins. That is exactly the stale overwrite race this PR is supposed to prevent.

Jepsen-style history:

1. Stored document is `A`, version `vA`.
2. Client 1 writes document `B` with `baseVersion=vA`.
3. Client 2 writes document `C` with `baseVersion=vA`.
4. Both requests pass `gutenberg_validate_persisted_crdt_document_base_version`.
5. Both writes proceed through normal `update_metadata`.
6. The final stored document is whichever write lands last. The other CRDT document is lost from persistence until some peer happens to merge and save it again.

PR 77890's PHP tests are sequential and do not catch this. See `origin/pr/77890:phpunit/tests/collaboration/persistedCrdtDocumentMeta.php:47` and `:59`.

Required fix: the authoritative write path needs an atomic predicate, for example `UPDATE wp_postmeta SET meta_value = <new> WHERE meta_id = <id> AND meta_value = <old>`, with a conflict if affected rows is zero. An early REST `409` check can stay, but it cannot be the only guard.

### 2. PR 77889 rejects stale writes without driving the advertised retry path

PR 77889's server-side filter returns `false` on stale writes:

- Version mismatch returns `false` at `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:151`.
- Lost CAS race returns `false` at `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:169`.

In WordPress core, a non-null return from `update_post_metadata` short-circuits `update_metadata()` and is cast to bool. The REST meta update layer treats a false `update_metadata()` result as a generic `rest_meta_database_error`, not as the PR's intended CRDT conflict.

The client-side code in 77889 does not catch a stale-write error and refetch. In `persistCRDTDoc`, it awaits `dispatch.saveEntityRecord(...)` at `origin/pr/77889:packages/core-data/src/resolvers.js:261`; if the save failed under the default `throwOnError=false`, `saveEntityRecord` returns no `savedRecord`, and `persistCRDTDoc` exits at `origin/pr/77889:packages/core-data/src/resolvers.js:266`.

The refetch/merge/retry block at `origin/pr/77889:packages/core-data/src/resolvers.js:286` only runs after a successful save returned a record. That is the wrong side of the branch for stale rejection.

Required fix: stale writes must surface as a distinct client-detectable conflict, preferably REST `409` with `code=rest_crdt_document_stale`, and `saveEntityRecord` or the persistence caller must handle that exact failure.

### 3. PR 77889 treats every successful version increment as a conflict

On an accepted existing-row write, PR 77889 increments the stored numeric `baseVersion`:

- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:155`

But the client compares the saved server version to the version it sent:

- Sent version captured at `origin/pr/77889:packages/core-data/src/resolvers.js:252`.
- Server version parsed at `origin/pr/77889:packages/core-data/src/resolvers.js:270`.
- If they differ, it assumes another client won a race at `origin/pr/77889:packages/core-data/src/resolvers.js:278`.

On a normal uncontended successful save, `serverVersion` should be `baseVersionSent + 1`. Therefore this condition fires on ordinary success. The code then attempts a refetch/merge/save cycle at `origin/pr/77889:packages/core-data/src/resolvers.js:286`.

This causes extra writes and version churn in the common path. It also makes the code's conflict signal ambiguous: version changed because our CAS succeeded, not because another client changed the document.

Required fix: a successful CAS is success. A conflict is the failed atomic write or explicit REST `409`, not "server returned the next version."

### 4. PR 77890 leaves stale `_crdt_document` in autosave payloads

PR 77890 keeps the existing autosave behavior that sends `meta` in autosave payloads. In the autosave branch, `meta` is included among persisted keys at `origin/pr/77890:packages/core-data/src/actions.js:740`.

With PR 77890's server validation, an autosave carrying an old `_crdt_document` can now be rejected as a stale CRDT update. The autosave path does not have the CRDT conflict retry logic; that retry logic only exists in the non-autosave branch starting at `origin/pr/77890:packages/core-data/src/actions.js:778`.

PR 77889 handles this correctly by stripping `_crdt_document` from autosave meta:

- `origin/pr/77889:packages/core-data/src/actions.js:692`
- `origin/pr/77889:packages/core-data/src/actions.js:698`

Required fix: keep `_crdt_document` out of autosaves. Autosaves should not persist CRDT sync state.

## Medium-Severity Findings

### 5. Both PRs have a first-write race

PR 77889 lets WordPress perform the first insert when no row exists:

- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:190`

PR 77890 adds an `add_post_metadata` filter to reject additions if a value exists:

- `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:270`

That narrows the race, but it is still a check before an insert. Without a unique database constraint, lock, or transaction, two first writers can both observe no row and both insert. WordPress registered meta with `'single' => true` does not create a database uniqueness guarantee.

Required fix: serialize the first insert. Options include a database uniqueness strategy, an application lock around `_crdt_document` initialization for a post, or custom storage with a unique key on `(post_id, meta_key)`.

### 6. PR 77889's initial-version hook is not a WordPress metadata hook

PR 77889 registers:

- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:216`
- Hook name: `pre_update_post__crdt_document`

WordPress metadata update exposes `update_post_metadata`, `add_post_metadata`, and sanitization hooks such as `sanitize_post_meta_<key>`. I found no `pre_update_post_<meta_key>` hook in the core metadata path. The claimed first-write injection therefore does not run.

The practical consequence is that first insert stores whatever `baseVersion` the client serialized. In the current JS this is usually `0`, but the version is not server-owned on creation.

Required fix: do not rely on that hook. If numeric versions are used, the server must set the initial version inside the authoritative insert/write path.

### 7. PR 77890 uses a custom non-cryptographic checksum as the concurrency token

PR 77890 computes versions with a hand-rolled 32-bit-pair FNV-style checksum:

- JS: `origin/pr/77890:packages/sync/src/utils.ts:85`
- PHP: `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:112`

This is probably fine for accidental corruption detection, but it is weak as a correctness token. A collision means a stale write can be accepted as if it were based on the current document. This is not primarily an authorization issue, but it is avoidable protocol fragility.

Required fix: use a collision-resistant digest such as SHA-256 over the serialized `document`, or compare exact stored document identity in the atomic write predicate and keep the checksum as a convenience value.

### 8. PR 77889 manually bypasses part of WordPress metadata behavior

PR 77889 directly updates `$wpdb->postmeta`:

- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:160`

It deletes the post-meta cache and fires `updated_post_meta`:

- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:173`
- `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:185`

That is not the full WordPress metadata update path. If Gutenberg takes over the write for this key, the replacement should explicitly decide which hooks and cache behaviors it must preserve, then test them. A narrow custom path is acceptable here, but it needs to be honest about what it is bypassing.

## What Each PR Gets Right

### PR 77889

- It recognizes that correctness requires an atomic database predicate, not just a preflight check.
- The existing-row CAS shape at `origin/pr/77889:lib/compat/wordpress-7.0/collaboration.php:160` is the essential primitive.
- It strips `_crdt_document` from autosave payloads, which avoids stale autosave writes.
- The patch is small enough that the intended invariant is visible.

### PR 77890

- It uses a content-derived version, avoiding a server counter hidden inside a client-supplied JSON blob.
- It returns an explicit REST conflict: `rest_crdt_document_stale` with status `409` at `origin/pr/77890:lib/compat/wordpress-7.0/collaboration.php:219`.
- The client handles stale-save conflicts in the save path at `origin/pr/77890:packages/core-data/src/actions.js:806`.
- It adds `applyPersistedCRDTDoc` to merge a freshly fetched server CRDT document into the local Y.Doc without immediately requesting another persistence write.
- It adds PHP and JS tests, even though the most important concurrent histories are still missing.

## Audit Lenses

### Linus Torvalds / kernel-maintainer lens

The invariant should be simple: "A persisted CRDT document write commits only if it was based on the current persisted document." PR 77890 obscures that invariant across REST pre-insert filters, metadata filters, and normal WordPress update flow, but never creates a commit point. PR 77889 has a commit point, but the surrounding client state machine is confused.

The best implementation should make the invariant visible in one small server function and one client retry path.

### Kyle Kingsbury / Jepsen lens

The meaningful test is two concurrent writers from the same base. PR 77890 fails that model unless the database write is made conditional. PR 77889 handles the existing-row race better, but not first insert, and its client does not recover from the conflict signal it emits.

Tests should include at least:

- Two concurrent REST saves with the same `baseVersion`; exactly one succeeds.
- The loser receives a `409`, refetches, merges, and retries.
- Two concurrent first writes do not create duplicate `_crdt_document` rows.
- Autosave never mutates `_crdt_document`.

### Dan Luu / operations lens

PR 77890 will produce clearer logs and client behavior because conflicts are explicit REST errors. PR 77889 will look like generic save/meta failures and can silently skip the merge/retry path. Under load, 77889 also appears likely to double-save every successful CRDT persistence update.

### tptacek / security-review lens

Neither PR materially changes authorization. The risk is integrity of collaborative state. PR 77890's custom checksum is unnecessary attack surface for a concurrency token. PR 77889 lets the initial numeric version be client-controlled because the intended initial-version hook is not real.

### djb / small-TCB lens

The smallest trusted core is:

1. Parse persisted CRDT document.
2. Compute current version from the stored value.
3. Validate incoming base version.
4. Commit with an atomic predicate.
5. Return either the updated record or a typed conflict.

PR 77890 has too much non-authoritative checking. PR 77889 has the atomic predicate but spreads recovery logic into a resolver in a way that does not match the actual failure mode.

## Recommended Combined Design

Use PR 77890 as the base, then make these changes before merge:

1. Keep `baseVersion` as a document-content version, but use SHA-256 or exact stored-value comparison instead of the custom checksum.
2. Keep REST `409` conflicts for client ergonomics, but make the metadata write itself atomic.
3. Move the authoritative `_crdt_document` write into one narrow server path that either commits with CAS or returns a conflict.
4. Strip `_crdt_document` from autosave payloads, as in PR 77889.
5. Keep `applyPersistedCRDTDoc`, but add a bounded retry test where the second retry also conflicts.
6. Add PHP tests for concurrent existing-row updates and first-write races. Sequential stale-update tests are not enough.
7. Add a cross-language fixture test proving JS and PHP compute the same version for the same serialized document.

## Merge Recommendation

Do not merge either PR unchanged.

If choosing one branch to continue from, continue from PR 77890. It has the better protocol, better client integration, and test scaffolding. Pull in 77889's CAS idea and autosave stripping. Treat the lack of an atomic write in 77890 as a release blocker, not a follow-up.
